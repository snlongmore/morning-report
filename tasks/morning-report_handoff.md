# Morning Report Handoff

> **Written:** 2026-07-26 | **Branch:** main

## Current State

The pipeline runs daily at 05:00 via launchd and has been producing a report every morning, but two things had degraded since the laptop migration and both are now addressed in code.

French generation had failed on every run from 23 to 26 July, so those four reports shipped with `*Traduction indisponible*` and `*Vocabulaire indisponible*` in place of the content. Email has been skipped on every run since 15 July. Today's report has been regenerated by hand and is complete. 191 tests pass.

Two secrets still need to be provisioned by hand, and until they are, the scheduled run will keep behaving as it did this week. See **Outstanding** below.

## What Was Wrong

**French generation.** `claude -p` failed with `Failed to authenticate: OAuth session expired and could not be refreshed`, five to ten times per run. The diagnosis took some ruling out, because the obvious explanations were all wrong:

| Suspected cause | Ruled out by |
|-----------------|--------------|
| No network | On 25 July all three gatherers completed live HTTPS calls in 7s, then `claude -p` failed 16ms later, ten times over 5 minutes |
| Locked keychain | Login keychain is `no-timeout`. A throwaway launchd job confirmed keychain read, keychain write and a live `claude -p` call all succeed from that context |
| Stale credential in the environment | `~/.zshenv` does not exist, and neither `CLAUDE_CODE_OAUTH_TOKEN` nor `ANTHROPIC_API_KEY` is set anywhere |
| CLI version change | Ran 2.1.209 throughout 22-26 July, only updated to 2.1.220 on the 26th at 07:51 |

What remains, and this is inferred from the evidence rather than documented behaviour, is that the interactive OAuth access token lasts about 7.5 hours and its refresh path does not work from a launchd job. The 16ms failure is too fast for any network round trip, so no refresh is being attempted at all. Whether the 05:00 job succeeded therefore depended on how late Claude Code had been used the previous evening, which is exactly the pattern in the logs: fine for a week, then reliably bad from the morning after a run that had no network.

The trigger was 22 July. The machine woke with no network, that run's `claude` calls timed out and then returned a 401, and it never recovered afterwards.

**Email.** The Gmail app password lives in the Keychain and did not survive the migration. The previous session flagged this and handed it back; it was never set.

## Changes Made

| File | Change |
|------|--------|
| `src/morning_report/keychain.py` | **New.** Generic Keychain get/set, plus named helpers for the Claude token. Service constants for both secrets live here. |
| `src/morning_report/report/emailer.py` | Keychain functions now delegate to the shared module rather than shelling out themselves. Public API unchanged. |
| `src/morning_report/french_gen.py` | `_build_cli_env()` supplies `CLAUDE_CODE_OAUTH_TOKEN` from the Keychain and warns when there isn't one. `_cli_error_message()` pulls the real reason out of the CLI's stdout JSON envelope. `_is_auth_error()` plus a `_fatal` flag stop the retry loop dead on auth failures. `_CLI_TIMEOUT` 300→180, `_MAX_RETRIES` 10→5. |
| `src/morning_report/cli.py` | New `set-claude-token` command. |
| `scripts/run-morning-report.sh` | Exports `CLAUDE_CODE_OAUTH_TOKEN` from the Keychain, warning loudly if absent. Network wait now probes with a real HTTPS request instead of a DNS lookup, times itself against the wall clock instead of counting its own sleeps, and allows 300s instead of 120s. |
| `CLAUDE.md` | Documented both secrets and the reason the Claude token is needed. |
| `tests/test_french_gen.py` | Autouse fixture stubbing the Keychain lookup (patching `subprocess.run` patches it on the shared module, so it was swallowing the CLI mocks' side effects). 16 new tests across error extraction, auth detection, fail-fast retry, and env building. |
| `tests/test_keychain.py` | **New.** 9 tests. |
| `tests/test_emailer.py` | Keychain patch targets repointed at the shared module. |

Retry budget now fits inside the pipeline watchdog: 5 × (180 + 30) = 1050s against a 1200s limit. It did not before, at 10 × (300 + 30) = 3300s, which is why the 22 July run was killed mid-retry instead of finishing and writing a report.

## Outstanding

Two commands only you can run. Until both are done, the 05:00 job keeps producing a French-less report and skipping email.

```
claude setup-token                       # then paste the token into the next command
.venv/bin/morning-report set-claude-token

.venv/bin/morning-report set-password    # Gmail app password
```

Then confirm the whole thing works from the scheduler's own context:

```
launchctl kickstart -k gui/$UID/com.snl.morning-report
tail -f ~/Library/Logs/morning-report.log
```

Everything from the March and July sessions is still uncommitted on `main`, including these changes.
